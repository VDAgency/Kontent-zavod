## D-010 — Отложенные проверки только за тем, что меняется само

**Дата:** 2026-08-21 · **Статус:** принято

**Решение.** Проверка по расписанию ставится только за внешним событием, которое
происходит без участия человека: упавший CI, комментарий ревьюера, ответ сервиса.
За тем, что ждёт решения пользователя, проверка не ставится. Все проверки,
поставленные за сессию, снимаются на `/finish`.

**Почему.** На PR #3 была заведена почасовая проверка «не смёржен ли». PR ждал
решения автора, и проверка отработала девять раз подряд с одинаковым ответом:
токены потрачены, лента засорена, результат не приблизился. Решение человека
по расписанию не появляется — его нужно запросить один раз и ждать.

**Альтернативы.** Увеличить интервал — уменьшает шум, но не устраняет причину.
Не ставить проверки вовсе — теряем реальную пользу там, где событие приходит
само и требует быстрой реакции.

**Последствия.** Часть событий придётся узнавать в начале следующей сессии,
а не в момент появления. Для проекта из одного человека это приемлемо.

Заодно зафиксировано в `CLAUDE.md`: команды «стоп» не существует, закрытие вкладки
ничего не сохраняет и не мёржит. Работу сохраняет только `/finish`,
мёрж в `main` — отдельное решение пользователя.

## D-009 — `marketing` и `superpowers` — обязательные наборы скиллов проекта

**Дата:** 2026-08-20 · **Статус:** принято

**Решение.** Два набора скиллов входят в оснастку «Контент-завода» постоянно,
а не подключаются под случай:

- **`marketing`** (Anthropic) — при написании промтов для статей и постов,
  сверке с правилами тона, SEO-разборе;
- **`superpowers`** (obra/superpowers-marketplace) — при разработке: TDD,
  системная отладка, планы, code review, параллельные агенты.

`superpowers` объявлен в `.claude/settings.json` через `extraKnownMarketplaces`
и `enabledPlugins` — на уровне проекта, а не машины.

**Почему.** Первоначальный план был отложить маркетинговые скиллы, «чтобы не грузили
контекст». Проверка показала, что предпосылка неверна: скилл держит в контексте
только имя и строку описания, тело читается при вызове. Откладывать нечего.

По `superpowers` автор подтвердил опыт использования на своей машине: с ними
подагенты работают чётче. Проверка состава подтвердила — это набор скиллов
без MCP-серверов, то есть дёшево по контексту.

**Альтернативы.** Подключать под задачу — лишний шаг ровно в тот момент, когда
нужно работать. Не подключать вовсе — терять готовую методологию там, где
у проекта один исполнитель и нет второй пары глаз.

**Последствия и риски.**

1. `superpowers` ставит собственный SessionStart-хук поверх нашего. Несколько
   таких хуков сосуществуют, но проверить вывод в первой же сессии после установки.
2. Marketplace сторонний, вне каталога аккаунта: обновления приходят из чужого
   репозитория. При странном поведении сессии проверять его первым.
3. Объявление в настройках проекта не равно установке: по документации плагин
   из внешнего источника считается неустановленным, пока не поставлен явно.
   В облачной сессии контейнер временный — возможно, потребуется `/plugin install`.
4. Настоящее ограничение по скиллам — не контекст, а однозначность: похожие скиллы
   конкурируют. Правило — один скилл на задачу, дубли не подключаем.

## D-008 — Состав MCP-серверов: ядро сейчас, остальное под задачу

**Дата:** 2026-08-20 · **Статус:** принято

**Решение.** В `.mcp.json` попадает только `n8n-mcp`. Context7 и GitHub уже
предоставлены на уровне аккаунта и облачной сессии — их конфигурация описана
в `docs/TOOLS.md` для локального CLI, но в файл не дублируется. Playwright
добавляется на этапе 2 вместе с сайтом, PostgreSQL — при первой отладке логов
n8n в базе.

**Почему.** Дублировать сервер, который уже подключён, нельзя: получится два
экземпляра одних и тех же инструментов. Отложенные серверы — вопрос контекста:
описания инструментов каждого сервера грузятся в **каждую** сессию, и набор
«на всякий случай» вытесняет то, ради чего сессия открыта. Playwright без сайта
проверять нечего, PostgreSQL до первой отладки не нужен.

Переменные n8n заданы как `${VAR:-}`: пока VPS нет, сервер поднимается в режиме
документации и валидации нод — это уже полезно при проектировании workflow.
Появится VPS — заполняется `.env`, `.mcp.json` править не нужно.

**Альтернативы.** Подключить всё сразу — удобно один раз, дорого каждую сессию.
Не заводить `.mcp.json` вовсе — настройка не переживает смену сессии (см. D-002, D-006).

**Последствия.** При работе из локального CLI Context7 и GitHub придётся добавить
руками по готовым блокам из `docs/TOOLS.md`. Это принятая плата за отсутствие
конфликта в основном, облачном сценарии.

Отдельно: ключ n8n API в community-редакции даёт полный доступ ко всем workflow,
credentials и логам инстанса. Он приравнивается к паролю от сервера и живёт
только в `.env`.

## D-007 — n8n на своём VPS, в Docker Compose, workflow версионируются в git

**Дата:** 2026-08-20 · **Статус:** принято

**Решение.** n8n разворачивается на собственном VPS автора. Способ установки —
Docker Compose. Экспорт workflow в JSON хранится в этом же репозитории
(`automation/workflows/`).

**Почему.** Свой VPS даёт полный контроль над данными и не упирается в лимиты
исполнений облачного тарифа, что важно для ежедневного расписания. Docker Compose —
потому что обновление и откат делаются одной командой; установка npm-ом на голую
систему превращает каждое обновление в отдельную работу.

Workflow в git — потому что это ровно та же логика, что и с `docs/STATE.md` (D-002):
то, что живёт только в интерфейсе, не переживает аварию и не имеет истории.
Дополнительная выгода: история изменений workflow — готовый материал для кейса,
видно, как решение эволюционировало.

**Альтернативы.** Облако n8n — быстрее стартовать, но лимиты исполнений и данные
на чужой стороне. Локально на машине автора — не работает, нужен постоянно доступный
HTTPS-адрес для вебхуков и расписания.

**Последствия.** Ответственность за бэкапы, обновления и безопасность на авторе.
Ключ `N8N_ENCRYPTION_KEY` становится критическим секретом: без него не восстановить
credentials из бэкапа. Появляется потребность в домене и HTTPS — тот же домен нужен
сайту из этапа 2, покупается один раз.

## D-006 — Оснащаем сессию до постройки workflow, а не по ходу

**Дата:** 2026-08-20 · **Статус:** принято

**Решение.** Перед этапом 1 отдельным шагом подключаем инструменты: Context7 для
актуальной документации, MCP-сервер n8n для работы с реальным API, при необходимости
плагины и скиллы. Набор фиксируется в `.mcp.json` в репозитории, чтобы подхватывался
в каждой новой сессии, а не настраивался заново.

**Почему.** n8n меняется быстро, и память модели устаревает — без Context7 и n8n MCP
workflow будет строиться по устаревшим представлениям об API, а ошибки всплывут
уже в проде. Дешевле потратить одну сессию на оснастку, чем отлаживать вслепую.

Второе: настройка, сделанная только в интерфейсе, не переживает смену сессии.
В репозитории она переживает, ровно по той же логике, что и `docs/STATE.md` (D-002).

**Альтернативы.** Подключать инструменты по ходу, когда упрёмся — растягивает отладку
и роняет фокус посреди работы. Строить без MCP вообще — рабочий вариант для простого
workflow, но здесь их будет несколько, и цена ошибки растёт с каждым.

**Последствия.** Этап 1 сдвигается на одну сессию. Плагин Superpowers пока
не проверен: сначала смотрим, что он делает, потом решаем, ставить ли —
непроверенный инструмент в конвейере хуже, чем его отсутствие.

## D-005 — Первая автоматизация: ежедневный дайджест в Telegram, и она же первый кейс

**Дата:** 2026-08-20 · **Статус:** принято

**Решение.** Этап 1 — не написание первого кейса вручную, а сборка n8n-workflow:
сбор материалов из технических источников (RSS, Telegram-каналы), отбор подходящего
под тематику канала, ежедневная публикация в Telegram плюс сторис-анонс со ссылкой.
Сам процесс постройки этого workflow документируется и становится первым кейсом.

**Почему.** Автор — разработчик автоматизации, у которого нет времени на контент.
Первая автоматизация обязана снимать его собственную рутину, иначе она не окупится.
Ключевое: этот workflow одновременно решает обе задачи — наполняет канал ежедневно
и служит доказательством компетенции, потому что «я автоматизировал свой контент
и вот как» проверяемо ровно тем каналом, где опубликовано.

**Альтернативы.** Сначала написать кейс руками — надёжнее по срокам, но не снимает
рутину и откладывает то, ради чего проект затевался. Начать с сайта и блога —
сайта пока нет, это отдельная работа, она не блокирует Telegram.

**Последствия.** Дайджест из чужих новостей сам по себе делает автора библиотекарем,
а не экспертом. Поэтому в `PROJECT.md` зафиксировано правило: к каждой новости —
собственный вывод. Это единственная ручная часть, и её нельзя отдавать автоматике целиком.

Второе последствие: блог на сайте выпадает из волны 1 до появления сайта.
Волна 1 временно состоит из одного Telegram.

## D-004 — Аудиторию выбираем контентом, а не заранее

**Дата:** 2026-08-20 · **Статус:** принято

**Решение.** Сегмент не фиксируем. Записываем три гипотезы (H1 бизнес, H2 блогеры
и эксперты, H3 агентства), помечаем каждый материал гипотезой, через 10–15 публикаций
смотрим, где отклик и откуда заявки.

**Почему.** Сегмент не выбран, и кабинетным размышлением он не выберется — данных нет.
Контент здесь дешевле опроса: он всё равно производится, гипотеза добавляет к нему
одну строку метаданных.

**Альтернативы.** Выбрать B2B волевым решением — риск полгода писать не тем.
Провести исследование аудитории — время, которого нет, оно и есть исходная проблема.

**Последствия.** Первые 10–15 материалов будут разнородными, охват размажется.
Это принятая плата. Через 15 публикаций обязательно вернуться в `PROJECT.md`
и дописать вывод — иначе гипотезы останутся навсегда непроверенными.

## D-003 — Каналы запускаем волнами, а не все сразу

**Дата:** 2026-08-20 · **Статус:** принято

**Решение.** Десять каналов (Telegram, блог на сайте, vc.ru, Дзен, VK, YouTube,
Rutube, Instagram, Threads, Одноклассники) разбиты на четыре волны. Волна 1 —
Telegram и блог на своём сайте. Следующая волна запускается только когда предыдущая
работает без ручного труда.

**Почему.** Исходная проблема — нехватка времени. Десять каналов одновременно эту
проблему усиливают, а не решают: десять форматов, десять расписаний, десять причин
всё бросить. Telegram выбран домом, потому что туда можно вести всех остальных.
Блог на сайте — потому что это единственный актив, который принадлежит автору:
площадка может закрыться или сменить алгоритм, домен останется.

**Альтернативы.** Запустить всё сразу — типовой способ выгореть за месяц и остаться
с десятью мёртвыми каналами, что хуже для репутации, чем их отсутствие.
Начать с видео (YouTube/Rutube) — самый дорогой формат по времени, плохой первый шаг.

**Последствия.** Присутствие в сети будет нарастать медленнее, чем хочется. Взамен
оно не обнулится через месяц. Порядок волн — не догма: если vc.ru начнёт приводить
заявки раньше блога, приоритет меняем и пишем сюда новое решение.

## D-002 — Контекст сессии живёт в `docs/STATE.md`

**Дата:** 2026-08-20 · **Статус:** принято

**Решение.** Текущее состояние проекта хранится в одном коротком файле `docs/STATE.md`,
он же обновляется в конце каждой сессии.

**Почему.** История чата не переживает новую сессию. Один короткий файл читается
быстро и не расползается; длинная история уходит в `JOURNAL.md`.

**Альтернативы.** Держать всё в `CLAUDE.md` — файл распухает и его перестают читать.
Держать состояние в issues на GitHub — лишний переход, неудобно с телефона.

**Последствия.** Забыли обновить `STATE.md` — следующая сессия стартует вслепую.
Поэтому обновление зашито в команду `/finish`.

## D-001 — Markdown + git как основа, без базы данных

**Дата:** 2026-08-20 · **Статус:** принято

**Решение.** Весь проект — текстовые файлы в git.

**Почему.** Читается и правится с телефона, версионируется, не требует инфраструктуры,
Claude работает с этим напрямую.

**Альтернативы.** Notion / БД / CMS — удобнее для чтения, но добавляют интеграции
и точки отказа на старте.

**Последствия.** Когда объём контента вырастет, понадобится индекс или поиск.
Это вход в отдельное решение, не сейчас.
